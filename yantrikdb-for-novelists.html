YantrikDB — capabilities overview

A cognitive memory engine for AI agents and apps: vector search, a knowledge graph, a temporal model, decay, and conflict detection in one embedded engine. Notes below on how it lines up with a novel-writing app.

Engine v0.7.22 Rust core · Python + MCP Embedded · single file Local-first, offline MIT (MCP) / AGPL (engine)

What it is

YantrikDB stores facts as memories rather than rows. You write in natural language and query in natural language; the engine decides what's relevant using semantic similarity plus recency, importance, and graph connections. It runs embedded — a single SQLite file, no server process — and works offline. The Rust core is wrapped by a Python package (yantrikdb) and an MCP server (yantrikdb-mcp) that exposes the same operations as tools to Claude, Cursor, Windsurf, or any MCP client.

It's built around cognitive operations — record, recall, relate, think — not SQL, and it does background work between calls (consolidation, conflict scanning, decay).

Current capabilities (v0.7.22)

Each ships today across the engine, the Python package, and the MCP server.

Five indexes, one engine

Vector (HNSW), graph (entities), temporal (events), decay heap, and key-value — queried together.

Relevance-conditioned recall

Blends semantic similarity, temporal decay, importance, graph proximity, and retrieval feedback. Weights auto-tune from usage.

Knowledge graph

Entity relations, profile aggregation, relationship-depth queries, and memory↔entity linking for graph-boosted recall. relate · get_edges · entity_profile

First-class record links

Link memory to memory: advances, supersedes, contradicts, supports, questions, derived_from, or custom:<name>. Recall can expand linked records.

Conflict detection & resolution

Contradicting facts become typed, prioritized conflict segments you resolve explicitly — no silent guessing. scan_conflicts · resolve_conflict

Think / consolidate

think() merges similar memories, scans for conflicts, mines cross-domain patterns, and evaluates triggers.

Memory types

Semantic (facts), episodic (events), procedural (strategies) — each carrying importance, valence, domain, source, certainty, timestamps.

Temporal awareness

Decay models forgetting; stale() / upcoming() surface fading high-importance facts and approaching deadlines.

Proactive triggers

Flags what's worth surfacing: unresolved conflicts, decaying important facts, detected patterns — all grounded in stored data.

Multi-device CRDT sync

Append-only replication log; memories and graph edges merge conflict-free. Tombstones make "forget" propagate.

Sessions

Group a working session's writes; auto-computes memory count, topics, average valence, duration.

Namespaces

Isolated partitions in one database — e.g. one per book or series.

Embedded & private

Single SQLite file, no server, data stays local. A separate yantrikdb-server adds Raft-replicated cluster mode if needed.

Zero-setup embeddings

Bundled ~7 MB embedder (~89% of MiniLM quality). One line swaps in a stronger model when wanted.

MCP + framework adapters

Drop-in MCP server, plus LangChain, CrewAI, and OpenAI-Agents adapters.

Decoupled write path

Two-tier LSM vector index: foreground writes touch a small delta; HNSW work amortizes on a background thread, so writes never starve reads.

Why selective recall matters here

Token cost stays flat as the bible grows; precision rises with more data. (From the repo's benchmark.)

At ~500 facts a stuffed bible already exceeds a 32K window; at 5,000 it fits in no window. YantrikDB stays near 70 tokens per query.

Using it

As a Python library, or over MCP with no integration code.

Python — a story bible in ~25 lines

import yantrikdb

db = yantrikdb.YantrikDB.with_default("novel_bible.db")   # single local file

# 1. store canon facts
db.record("Aria Veth has storm-grey eyes and fears deep water.",
          importance=0.9, domain="character")
clue = db.record("In ch.3 Aria flinches at the harbour at dusk.",
                 importance=0.7, domain="plot")

# 2. character / faction graph
db.relate(src="Aria Veth", dst="House Veth", rel_type="member_of")
db.relate(src="House Veth", dst="House Corin", rel_type="blood_feud_with")

# 3. fuzzy recall — no exact keywords needed
for r in db.recall("what is the protagonist afraid of?", top_k=3):
    print(r["score"], r["text"])

# 4. link a plant to its payoff
db.record_with_links(
    text="In ch.18 Aria nearly drowns escaping the harbour ambush.",
    links=[{"target_rid": clue, "link_type": "custom:pays_off"}])

# 5. consistency check
db.record("Aria Veth's eyes are bright green.")   # contradicts canon
db.think()                                       # runs conflict scan
for c in db.get_conflicts(status="open"):
    print("conflict:", c)

db.close()

MCP — expose the same operations to an AI assistant

// .mcp.json
{
  "mcpServers": {
    "yantrikdb": {
      "command": "uvx",
      "args": ["yantrikdb-mcp"],
      "env": { "YANTRIKDB_DB_PATH": "./novels/storm-veth.db" }
    }
  }
}

The assistant then has remember · recall · relate · graph · record_with_links · recall_with_links · conflict · think as callable tools — the writer just talks, the model calls the right one.

Notes & limitations

Suggests, doesn't auto-edit

Conflict detection is semantic/heuristic, not a logic prover — it flags likely contradictions for review.

Embedded by design

One file, ideal for desktop/offline. Multi-user cloud needs the separate yantrikdb-server (Raft cluster mode).

Licensing

MCP server is MIT; core engine is AGPL. Fine for SaaS / self-host; check before shipping a closed-source binary.

Embeddings are tunable

Default bundled model is ~89% of MiniLM at 7 MB; swap in a stronger model with one line for sharper recall.
